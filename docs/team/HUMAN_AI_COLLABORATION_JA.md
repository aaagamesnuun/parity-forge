# Parity Forgeにおける人間・モデル・プログラムの分業

## 基本原則

人間、設計を助けるモデル、決定論的プログラム、独立監査を一つの「AI」にまとめない。それぞれの判断と証拠能力が違うからである。目的は人間を研究助手にすることではなく、少ない人間の判断を次のルールの具体的な差へ変換することにある。

運用の背景は[発見方法の再設計](../reviews/2026-09-08-discovery-reset-and-human-ai-loop-ja.md)、固定条件は[CHARTER](../CHARTER.md)、現在の入口は[PROJECT_STATE](../PROJECT_STATE.md)にある。

## 誰が何を担うか

| 担当 | 主な責任 | 単独では認定できないもの |
| --- | --- | --- |
| 人間のプロダクト所有者 | 楽しさ、再戦意欲、目的、公開、時間・費用、不可逆な選択 | solver結果、全合法手の終了性、再現性 |
| 設計モデル | 骨格案、反例、実装案、実験計画、結果解釈、次の一変更 | 面白さ、絶対的な深さ、未来の全AIへの耐性 |
| DSL・engine | 権威あるルール、合法手、遷移、終局、棋譜再生 | 候補の価値判断 |
| generator | 凍結範囲から定義を作る | 生成外のゲーム空間の不存在 |
| agent・evaluator | 限定能力で対局・局面評価を行う | 人間の代役、完全な公平性 |
| exact solver・証明器 | 指定範囲の勝敗や命題を証明する | 面白さ、実用上の学習曲線 |
| experiment runner | 順序、上限、claim、raw結果、失敗を保存する | 結果の意味づけ、後付けルール変更 |
| 独立reviewer | 数学、source、保存証拠、境界の不一致を探す | 新しい製品条件の決定 |

一人または一つのagentが複数役を担っても、責任境界は混ぜない。実装者の集計だけで受入れず、別の読み取り専用監査を置く。

## 有限な一周

1. 人間が目的と硬い条件を示す。
2. 設計モデルが、狙いの異なる少数の骨格を出す。
3. 静的検査で、機械的非対称性、規則整合、全合法プレイの有限単独勝者を確認する。
4. 定義、方策、seed、評価、予算、停止条件を結果を見る前に固定する。
5. 通常プログラムが合法手生成、対局、探索、再生、集計を実行する。
6. 独立reviewerがsourceと保存証拠を読み、登録どおりの実行か確認する。
7. 設計モデルが、成立違反、証明済み欠陥、限定観測、`UNKNOWN`を分けて解釈する。
8. 重大な既知欠陥がなく、未確認点を説明できる最大二案を人間へ渡す。
9. 短い試遊感想から一つの仮説を作り、次版で一要素だけ変える。

これはモデル自身の重みを自動更新する学習ではない。生成器、評価器、方策、ルール、作業配分を比較可能な単位で改善するループである。一度に複数を変えた場合、どれが効いたかは主張しない。

## モデルtokenと計算資源

モデルtokenは骨格生成、反例検討、必要な実装、代表例の読解、総括に使う。一手ごとの合法性、対局、探索、棋譜再生、集計は決定論的プログラムへ渡す。全棋譜を毎回モデルへ戻さず、分類別件数、境界事例、代表局面だけを選ぶ。

ただし、プログラムなら無制限に回してよいわけではない。CPU、状態、遷移、出力bytes、モデル作業回数の上限を先に置き、上限到達を勝敗や品質へ変換しない。[D-057](../DECISIONS.md)を参照。

## 証拠の段階

| 段階 | 言えること | 言えないこと |
| --- | --- | --- |
| 定義・静的成立 | schema、非対称性、必要条件が一致する | 実戦の公平性、面白さ |
| 全合法終了証明 | 無限局・引き分けが規則上ない | どちらが有利か、深さ |
| 短い戦略証明 | 対象に具体的な万能策や欠陥がある | 他版にも同じ欠陥がある |
| exact結果 | 固定定義の完全プレイ勝者または命題 | 有限能力同士の公平性、楽しさ |
| bounded対局 | 指定方策・seed・予算で起きたこと | 一般勝率、人間の反応 |
| 人間の試遊 | その人がその時どう迷い、感じたか | 普遍的人気やプロ水準の深さ |
| `UNKNOWN` | 登録した方法・予算では未確定 | 引き分け、深さ、合格、棄却 |

有限無引分ゲームのexact勝者は必ず片方になるため、それだけで不公平とはしない。反対に小標本が同数でも公平性証明にはならない。同じseedの先手違いや同一方策の深さ違いは有用だが、独立標本とは扱わない。

## 結果の四分類

- **成立しない**：無引分、非対称性、rule整合などの硬条件に違反する。
- **具体的な欠陥がある**：短い万能勝ち、目標不能など、射程付きの証拠がある。
- **まだ分からない**：予算切れ、方策不一致、小標本、未実行である。
- **人間に確かめる価値がある**：硬条件を満たし、所定の欠陥検査と開示が済んでいる。

最後の分類は公平性・深さ・面白さの認証ではない。人間へ渡せる状態を、未確認事項とともに示すhandoffである。

## 人間にしか聞かないこと

試遊では長い採点表より、次を聞く。

- どこで迷ったか。
- 負けた理由をどう感じたか。
- もう一度なら何を変えたいか。
- 残したい個性と、減らしたい負担は何か。

棋譜監査、seed選定、Plan管理、探索器選定は人間へ委ねない。「自分の判断で負けたと思えれば再戦したくなる」は検証中の仮説であり、反応と合わなければ更新する。

## Plan、ゲーム、実行ID

Plan番号は、凍結した研究上の問いを時系列に識別する番号であり、ゲームID、品質順位、成功回数ではない。問い、方法、予算、権限が変わると新しいPlanになる。[Plan番号の説明](../reviews/2026-09-08-plan0031-design-stage-ja.md)を参照。

- ルールはdefinition IDで識別する。
- ルール修正は`v0`、`v1`などのdefinition版で識別する。
- 一回の比較や計算はprotocol/run IDで識別する。
- Planは、それらをなぜ・どこまで使うかを定める研究単位である。

座標を一つ変えるたびにPlanを増やさない。逆に、結果を見て予算だけ増やし、古いPlanの続きに見せることもしない。

## one-shot、clone、研究所有権

本番experimentは、結果を見る前のregistrationと排他的claimを持つ。claimは成功・失敗・中断のいずれでも消費済みであり、clone上でも再実行しない。canonical outputを上書きせず、失敗記録を削除して「初回」に戻さない。[D-008/D-009](../DECISIONS.md)を参照。

cloneで通常許されるのは、文書を読む、既存証拠を検算する、合成fixtureをtestする、明示された新Planを実装する、といった作業である。新しい科学的問い合わせには、新しい権限、registration、ID、上限が必要になる。過去のraw結果を新しいruleやtiebreakで再解釈せず、訂正は追記する。

各作業単位では担当fileとintegration ownerを明示し、DSL、generator、evaluator、agent、search、runnerの変更を可能な限り分離する。実行前にsource hash、定義hash、manifest、上限を固定し、raw結果、runtime、failure、実exitを別々に保存する。機械可読DSLが権威で、説明文はそこから導出する。実践例は[Plan40](../plans/active/0040-connection-baseline.md)にある。

## 新しい参加者の開始順

1. [PROJECT_STATE](../PROJECT_STATE.md)を読む。
2. `docs/plans/active/`にある唯一のactive Planを読む。
3. [BACKLOG](../BACKLOG.md)を読む。
4. 担当範囲、実行owner、禁止された証拠領域を確認する。
5. 他担当のfileを編集せず、必要なAPIだけを早く共有する。
6. 本番commandは、Planと実行ownerが明示した場合だけ使う。

予算切れ、証拠不足、技術失敗、候補なしのときは範囲を広げず保存する。停止理由と残った不確実性が次のPlanの入力になる。この分業の目的はモデルが勝手に「良いゲーム」を宣言することではなく、機械が確かめられることを確かめ、価値判断を人間へ返し、その判断を次の検証可能な設計へ結びつけることである。
