# 発見を中心に据え直す計画と、人間・AIの分業

2026-09-08。ユーザーの「盤面は小さくなくてよい、ルールも極端に簡単でなくてよい、
自己改善と分業を含めて今後を深く計画してほしい」への回答。
追加確認で「引き分け禁止は維持したい」と明示された。

これは方針と次期作業の設計であり、新候補・新評価器の実行登録ではない。
Plan31は未登録・本番実行ゼロのまま保留する。過去の定義・基準・結果は変えない。
根拠は既存ソース、公開済み実験記録、原指示書、独立した記録／構成レビュー。
この検討では新しい対局、候補探索、ソルバー実行、回帰テストを行っていない。

## 結論

継続する価値はある。ただし「今の候補審査を繰り返す」のではなく、
**具体的なゲームを作り、その過程で発見方法も改善できるかを、有限の試行で確かめる。**
基盤の完成を先に目指さない。最初の成果は、正式な公平性認証ではなく、
明らかな欠陥を調べたうえで本人が考えて遊ぶ価値のある、動く一作である。

今までの結果から、非対称ゲーム全体が不毛だとは言えない。
一方で、盤面制限を外せば必ず見つかるとも言えない。
探索表現・測定器・作業配分を一緒に点検する必要がある。

## 1. 合意する条件

| 区分 | 今後の扱い |
| --- | --- |
| 固定条件 | 機械的に非対称な、二人用・決定論・完全情報のアブストラクトゲーム |
| 固定条件 | 初期状態からの**すべての合法プレイ**が有限に終わり、勝者がAかBの一人だけになる |
| 改善目標 | 考える理由、上達の余地、実用上の読み応え、再戦したさ |
| 改善目標 | 対象とする人・AIの能力範囲で、役割や先手による不利が大きすぎないこと |
| 後から調整可能 | 盤面サイズ・形、駒数、行動種類数、説明量、対局時間、簡潔さ |
| 研究運用上の必須事項 | ルールの一意性、実装との一致、再現性、上限と不確実性の記録 |

小盤面、各役割一種類の行動、極端な簡潔さ、完全な50対50は、新規候補の必須条件にしない。
異なる役割は異なる主観的な楽しさを生む必要まではなく、合法な手段・制約などに実質的な差があればよい。
単なる色名や回転で消える差は数えないが、任意のゲーム間の意味的非同型を完全証明する
巨大な新ゲートも作らない。確認した対称操作と機械的差を明記する。

「AIに完全には読み切られない」は、無限の計算資源や未来のAIに対して証明できない。
実用的な目標として残し、見つかった簡単な必勝策・容易な完全解は重要な欠陥として扱う。
UNKNOWNや盤面の大きさを深さの加点にはしない。人間が試す前に深さの絶対認証を要求しない。

D-055は維持する。有限・完全情報・無引分の固定ゲームには、最適プレイで片方の必勝戦略がある。
問題はその存在そのものではなく、簡単に実行できて駆け引きを消してしまうかどうかである。
予算切れはゲームの引き分けでも勝敗でもない。勝利・同時達成・行動不能の扱いは
各新定義に明記して審査し、既存結果への後付け勝者規則にはしない。

## 3. 広げるのは盤面だけでなく、ゲームの骨格

最初から任意のルールを無作為生成するのではなく、相手に働きかける理由のある
骨格を最大3種類選び、それぞれ最大4定義を比較する。以下は設計仮説であり、完成ルールではない。

| 骨格の例 | 非対称性と駆け引きの仮説 | 無引分への設計方針 |
| --- | --- | --- |
| 構築と妨害 | Aは経路・拠点を作り、Bは限られた妨害資源をどこへ配分するか選ぶ | 空間・未使用資源が不可逆に減ることを利用する |
| 少数の機動駒と多数の包囲駒 | 移動力と数の差を、突破・迂回・包囲の選択へつなげる | 後退・横移動も認めつつ、各行動の有限資源消費を設計する |
| 局所達成と広域支配 | 一方の集中攻撃に、他方が分散・封鎖・交換で応じる | 置いた資源や処理済み領域が戻らない段階進行を設計する |

単に別々の競走をするのではなく、相手の選択によって自分の優先手が変わる構造を狙う。
同じ骨格の座標違い12件を、12種類の独立したアイデアとは数えない。
既存のゲームで使われるメカニクスの組合せから始めてもよく、全要素の独創性は要求しない。
既存ルールの改変であれば由来を記録し、新規性を過大表示しない。

7×7や9×9、長方形、異なる駒種・複数行動も候補にできる。
これらの数字を新しい製品上限にはしない。初回実験の範囲だけを計算可能な量に固定する。
面白い相互作用が残ることを確認してから、盤面縮小とルール削減を行う。

無引分については、生成後に何でも証明しようとするより、終了理由を持つ設計から生成する。
最初は有限資源・非負整数の減少など少数の証明方式を使う。
終了までの残量と「どちらが有利か」は別の量にし、前進一本道へ戻らないようにする。
資源消費の直感だけでは足りず、全合法行動・全終局条件を覆う確認が必要である。

## 4. 基盤はどこまでできているか

**検証の部品はある。しかし、広い候補を継続的に作り、人間の反応から改善する一周は未完成。**

残すものは、機械可読ルール、合法手・遷移・終局、棋譜再生、ハッシュ、
小範囲の厳密解析、既存の故障テスト、変更と結果の追跡である。
旧生成器・古い簡潔さの足切り・terminal-only対戦・候補専用スクリプトを
新しい目的に対して無条件に再利用することはしない。

最初に足すものは、具体的な2つの骨格を動かすための最小限に絞る。

1. 盤面制限と必要な行動・資源を表せる、新版のルール表現または薄い接続層。
2. 定義・方策・シード・上限をデータで渡せる、共通の実験入口。
3. 終了証明、検査結果、代表局面、既知の弱点をまとめる出力。
4. 本人が実際に指せる最小の試作。オンライン対戦・会員機能・公開運用は後段。

この2骨格を表現力の代表例とする。第3骨格は同じ表現・入口で追加コードなしに扱える
場合だけ初回へ加える。できなければ初回は2骨格・最大8定義とし、数合わせの実装はしない。

基本案は既存基盤の最小拡張。ただし2つの骨格を表せない場合、恣意的に骨格を
旧DSLへ押し込む前に、既存のゲーム記述・対局基盤への薄い接続を比較する。
比較は独立した大移行計画ではなく、同じ2定義の表現・再生・終了条件を確認する
一度の小さな技術判断とする。採否は私が説明して決める。

Ludiiは幅広いルール表現とプレイヤーを持つ比較対象になるが、今回は導入しない。
既存の証拠形式との対応、決定論、ライセンス、無引分の意味を確認する必要がある。
全面移行やモデルの追加学習を、最初の試遊の前提にはしない。
[Ludii公式](https://ludii.games/)。

## 5. 三つの改善ループ

### ゲームを改善するループ

骨格と狙いを決める→定義を少数生成→普通のプログラムで検査・対局→
違う長所のある最大2案を提示→本人のプレイ→次の具体的修正、を一周とする。
似た高得点候補だけに集中せず、少数の種類別の保存枠を持つ。

「種類ごとに有望例を残す」という発想は、単一最高点だけを探さない
MAP-Elitesを参考にできる。初回は少数の手動カテゴリでよく、
高度な分類器や大きな探索基盤は不要である。
[MAP-Elites原論文](https://arxiv.org/abs/1504.04909)。

### 発見システムを改善するループ

失敗理由を一つ選ぶ→改善案を一つ作る→同じ対象・予算で旧版と比較→
未使用の確認例で退行を調べる→採用または不採用、を一周とする。
モデル自身の学習・重み更新ではなく、生成器・評価器・対戦方策・作業配分の改善である。

例えば「終局が遠いと全て同点になる」を直すなら、同じゲームを使って方策だけを変更する。
既知の短い必勝、死んだ目標、循環、実際に応手を変える必要のある局面など、
期待する性質が分かる対照を先に置く。全例を落とす検査器を成功扱いしない。
正の対照とは既知の性質を通す例であり、面白さの数学的正解が得られるという意味ではない。

生成器・評価器・方策・予算配分を同時に変えて、改善の原因を主張しない。
改善用と確認用はシードだけでなく、可能な範囲で骨格・仕組みも分ける。
確認例の結果を見て調整した時点で、その例は開発用に移り、もう未見確認とは呼ばない。
人間の反応を得る前に「面白さ予測の精度が上がった」とは言わない。

自己改善の採用条件は次のいずれかが改善し、独立した確認で重大な退行がないこと。

- 同じ費用で、既知の欠陥をより正確に見つける。
- 同じ費用で、検査不能のまま終わる割合を下げる。予算切れを合格へ変えるのは改善ではない。
- 同じ費用で、重複でない・成立条件を満たす設計の種類が増える。
- 本人に出す候補のうち、実際に考えて遊びたいものの割合が上がる。

最後の指標が最終目的に近いが、初期の少数試遊では誤差が大きい。
小さな改善は暫定採用とし、一般的な優越を宣言しない。

### 分業を改善するループ

本人へ何を見せたか→どの回答が設計判断を変えたか→説明・質問の負担を見直す。
質問数が多いこと、議論が長いことを協働の成功とは数えない。
人間の反応がない期間は技術的な作業だけを残予算内で進め、好みや試遊結果を捏造しない。

## 6. 評価と予算の運用を変える

結果を少なくとも四つに分ける。

- **成立しない**：無引分違反、ルール不整合、必須の非対称性がない。
- **具体的な欠陥がある**：短い万能勝ち、狙った目標の達成不能など。証拠と射程を保存する。
- **まだ分からない**：予算切れ、方策による不一致、小標本の勝率。悪いゲームの教師ラベルにしない。
- **本人に確かめる価値がある**：成立条件と所定の欠陥検査を満たし、未解決点を開示できる。

完全な公平性の確認は試遊の前提ではない。既知の重大欠陥のあるものは出さず、
短い必勝検査の対象・到達範囲・未確認点を示して、本人の判断を早い段階に入れる。
人間へ提示する基準は、新しい小試行の前に固定する。旧Planの基準は緩めない。

広いゲームの対戦には、少なくとも考え方の異なる2系統の方策を使える状態を目指す。
目標に向かう簡易方策と、局面評価つき探索や固定反復数のMCTSなどを比較する。
同一方策の深さ違いだけで独立な裏付けとしない。ランダムは故障検出の対照であり、人間の代役ではない。
勝率を50%へ近づけるようにAI予算を調整してから公平だと主張することも避ける。

探索・開発では失敗を見て次版を作ってよい。修正の由来と旧結果を残す。
確認実験は定義・方策・基準・予算を凍結し、後から都合よく変えない。
この二つを分けることは再現性を弱めることではない。
旧PlanのNO_FLAG、UNKNOWN、棄却、再試行禁止をそのまま保ち、新しい学習記録と混ぜない。

LLMを使うのは骨格設計、必要な実装、バッチの総括・改善案。
合法手生成・対局・検査・集計に局ごとのLLM呼出しを入れない。
失敗全件の長い棋譜を毎回読ませず、分類別件数と代表例だけを渡す。

## 7. 最初の有限キャンペーン案

以下は提案上限であり、今回消費する予算ではない。実行時の詳細は次の計画で登録する。
処理が遅い・候補が出ないという理由で自動的に上限を増やさない。

| 段階 | 上限案 | 必ず残す成果／停止点 |
| --- | --- | --- |
| 0：最小接続と校正 | 2骨格の表現確認、8〜12の小さな対照。改修対象を事前列挙し、下記作業上限を適用 | 旧版との対応、どの検査が使えるか。上限内に届かなければ未完成で停止 |
| 1：最初の設計比較 | 最大3骨格×各最大4定義＝12。第3骨格に追加実装が必要なら最大8。まず各8局以内、追加診断は最大4定義・各16局以内 | 最大2案の操作可能な試作、または届かなかった具体的理由 |
| 2：修正比較 | 次の12定義以内。一度に変更する研究要素は一つ | 何が改善／悪化したかを旧版・同予算で比較 |
| 3：最後の比較と判断 | さらに12定義以内。これで計3周・最大36新定義 | 続投・一作の磨き込み・方法の打切りを判断。第4周は自動開始しない |

各周の最初のAI設計と最後の総括をまとめ、通常2回、必要な改修の検討を含め最大3回の
モデル作業セッションを想定する。これは内部API呼出回数や正確なトークン数と同一ではない。
実装時には各セッションの入力・出力サイズと作業上限も設定する。
正確な使用量を取得できる部分だけ実測し、それ以外は推定と明記する。
セッション数だけで総トークン上限を保証できたとは報告しない。

段階0の技術選定・実装・レビューは別途最大3作業セッション、合計4作業時間以内を
初期提案とする（全回帰の機械実行待ちは別計上）。着手前に変更可能なファイル群と、
支える2骨格・必要な機能を固定する。新しい基盤課題を見つけても、その枠を自動で広げない。
上限内に動かなければ、理由と未完成差分を残して停止する。実装の試みを完了品とは報告しない。

候補の機械検証は初期案として各周4 CPU時間以内、校正2 CPU時間以内を別枠とし、
ノード／状態／遷移上限は校正後に具体化して実行前に固定する。
壁時計の緊急打切りは未完了を保存する安全弁とし、タイミング依存の結果を品質比較に使わない。
将来のコード変更に必要な全回帰テストと実装作業はこの候補計算費に隠さず別計上する。
初回コード改修の全回帰は一回を予定し、失敗時に無制限の修正・再実行へ入らない。
追加の改修が必要ならキャンペーンを未完了として停止し、原因と改訂予算を示す。

候補ごとの専用スクリプト／テストは増やさず、可能な限り定義データを変える。
コード変更完了前の`PYTHONPATH=src python3 -m unittest discover -s tests -v`は維持する。
データだけの新候補に毎回全体コード改修の儀式を持ち込まず、定義・終了証明・棋譜の検査を行う。
重い全回帰は共有部品の変更単位で行い、過去テストを削除・成功扱いしない。

第1周で試作に届かなければ、第2周の冒頭で「表現」「終了性」「評価器」「設計骨格」の
どこが詰まったかを特定する。同じ問題を抱えた座標微調整だけで続けない。
第3周までに本人が考えて遊べるものが出なければ、現在の方法への追加投資を止めて判断を返す。
これはゲーム発見の保証期限ではなく、成果なしに研究基盤だけが増えないための停止点である。

## 8. 人間とAIの分業

| 人間に持っていてほしい判断 | 私が担当する作業 |
| --- | --- |
| 何を楽しいと感じたか、もう一度やりたいか | 具体的な候補と比較可能な局面を用意する |
| どこで迷ったか、負けをどう受け止めたか | その発言から検証可能な設計仮説を作り、次版に反映する |
| 目的・時間・お金・公開などの境界を変えるか | 予算内の生成、実装、合法性、終了性、対局、失敗分類、記録 |
| 残したい個性、削ってよい負担 | 修正案の効果と副作用を示し、選んだ方針を保持する |

本人に棋譜監査、seed選定、Planの段取り、AIの技術選定まで頼まない。
好みの長いアンケートを前提にもせず、最大2案の実物を見て短く答えられる形にする。
基本の提示は「ルール、操作できる盤、考えどころ1局面、既知の懸念、未確認事項」。
想定する初回負担は一回10〜20分程度。長くなるゲームはまず局面からでもよいが、
部分試遊と完局した感想は別に記録する。
依頼する時間は各周最大1回・20分、計3回・60分以内をキャンペーン上限案とする。
各回最大2案であり、終わらなければ未完了として扱う。追加試遊を当然の義務にしない。

質問は原則「どこで迷った？」「負けた理由をどう感じた？」「もう一度なら何を変えたい？」。
答えが短くてもよく、必ず全部答える試験にはしない。
以前の「自分の判断で負けたと思えればまたやりたい」は有用な仮説だが、
本人の後の反応と合わなければ修正する。AIが説明を作れただけで納得感を認定しない。

分業の成功は、人間が研究助手として長時間働くことではない。
少ない人間の判断が、次のゲームの具体的な違いにつながることである。

## 9. 計画の扱いと今回の到達点

Plan31は`PAUSED_FOR_STRATEGIC_REPLAN / NOT_REGISTERED / PRODUCTION_COUNT_ZERO`。
静的に残ったCELL-1は未評価のまま保存し、悪いゲームとも有望なゲームとも認定しない。
凍結メタデータの整合性監査も未完了であり、直ちに実行できる状態とは扱わない。

次の実行単位はPlan0032を想定するが、この文書では番号を登録・起動しない。
役割は「一候補の合否判定」ではなく、この有限キャンペーンの最小接続と第1比較の設計。
候補は別ID、開発の修正は版番号、比較はバッチIDで管理し、座標を直すたびにPlanを増やさない。
確認の問い・方法・予算を変えるときだけ、新しい研究単位として記録する。

直近の実装開始時には、2骨格で必要になる差分を列挙し、最小の接続方式を選び、
対照と上限を固定する。自律的に実装と対局を無期限開始する許可として本提案を読まない。
今回の合意条件を運用文書へ反映し、過去計画の自動継続を保留にする。

## 外部研究から取り入れる範囲

巨大モデルの追加学習や論文の計算規模を、そのまま再現する計画ではない。
